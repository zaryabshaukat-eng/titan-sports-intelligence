# v0.3.0 Production Validation

## Required CI gates

Run lint, the backend test suite with coverage, Alembic offline upgrade/downgrade/upgrade SQL generation, Docker Compose configuration validation, and a backend image build. The repository workflow at `.github/workflows/backend-validation.yml` performs these gates on pull requests and `main`.

## Deployment sequence

1. Supply production secrets through the deployment environment; never use development identity credentials or the default secret.
2. Back up PostgreSQL and verify restore procedures before migration.
3. Run `python -m alembic upgrade head` against the deployment database, or use Docker Compose's `migrate` service, which gates API and worker startup.
4. Deploy API and worker together, then verify `/health`, `/ready`, and `/metrics`.
5. Alert on readiness failures, outbox backlog growth, retry/dead-letter increases, authentication failures, and slow-request counters.

## Recovery

Outbox rows are retained until publication and dead-lettered rows retain the failure reason. Recover a failed worker by restarting it; expired leases make abandoned events eligible again. Investigate dead-letter records before any manual replay, using their immutable raw payload, audit record, and event key for idempotency.

## Validation limits

The local suite runs PostgreSQL integration tests only when `TITAN_TEST_DATABASE_URL` points to an isolated migrated database. CI must add that service before treating live migration/data-preservation, large-batch throughput, memory, and concurrent-writer benchmarks as release gates. These are operational benchmarks, not assertions that can be truthfully produced without a database runner.
